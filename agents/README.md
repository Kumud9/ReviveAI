# ReviveAI Agents Module

This module contains the LLM-powered investigation and recommendation layer for ReviveAI.

## Role of the Agent
The `RecoveryAgent` is responsible for investigating a failed payment and recommending the most appropriate recovery intervention based on factual context and machine learning predictions.

**IMPORTANT: The LLM does NOT execute payments or recovery actions.**
It only generates a structured recommendation. The execution is handled strictly by downstream components:
`ML -> LLM Recommendation -> Policy Engine -> Guardrails -> Executor`.

## Input Context
The agent receives a heavily constrained JSON object containing:
- `FACTS`: Raw details about the payment, customer history, and failure diagnosis.
- `MODEL_OUTPUTS`: The recovery probability and expected recovery value generated by the Phase 2 ML model.
- `AVAILABLE_ACTIONS`: A list of explicitly permitted recovery actions.

## Output Schema
The agent must return a validated JSON object conforming to:
- `decision`: Must be one of `AVAILABLE_ACTIONS`.
- `confidence`: Float between 0.0 and 1.0.
- `reason`: String explaining the decision.
- `priority`: 'high', 'medium', or 'low'.
- `estimated_recovery_value`: Float.
- `requires_human_review`: Boolean.
- `evidence`: List of strings outlining key factors.

## Safety Boundaries
- **Strict Validation**: The agent validates the proposed decision against `available_actions`. If the LLM proposes an invalid action, the system forces a fallback to `human_escalation`.
- **Prompt Injection Defense**: Customer notes are isolated within the `FACTS` block, explicitly defined as untrusted data in the system prompt.
- **No Hallucinations**: Validations bound values like confidence and priority, stripping out hallucinated or out-of-range metadata.

## Human Escalation
The agent can recommend `human_escalation` for ambiguous, high-value, or legally sensitive failures. If the LLM fails or generates malformed output, the system defaults to this safe state.

## Testing Strategy
Tests are located in `tests/test_recovery_agent.py`. They use a mocked `LLMClient` to ensure deterministic, fast testing of the validation logic, prompt constraints, and error fallbacks without requiring a real LLM API key.
